# 代码生成与修改规则

## 核心原则：SKILL 驱动的代码操作

在创建任何文件、修改任何代码之前，你必须确认自己理解了该类型文件的约束。
这包括：框架约定的目录结构、该类型文件常用的渲染/执行机制、常见的坑。

对于本项目（HTML/CSS/JS 单文件项目），你尤其需要注意：
- Canvas 绘制是逐帧渲染的，每帧的绘制顺序和条件判断直接决定视觉效果
- 修改视觉效果时，先用关键词（如 strokeRect、stroke、ctx.fillStyle）搜索相关绘制代码
- 绝不重写整个文件来修一行渲染 bug

## 修改已有代码的标准流程

1. **理解问题**：用户说"不对"——先弄清楚是哪里不对。是视觉效果、逻辑行为、还是报错？
2. **搜索定位**：用 search_content 搜索相关关键词（函数名、CSS 属性、Canvas API、渲染关键字）
3. **局部读取**：用 read_file 带 start_line/end_line，只读问题相关区域（前后扩 10 行）
4. **精准替换**：用 replace_in_file 替换出问题的片段。old_str 必须和文件内容完全一致
5. **替换失败时**：不要退化为 write_file 重写全文件。扩大 read_file 范围，重新确认 old_str
6. **验证**：替换后，read_file 确认改动是否生效

## 新建文件的标准流程

1. 先调用 get_workspace_path 获取工作区路径
2. 用 write_file 创建文件，路径基于工作区路径拼接
3. 如果需要前后端分离，在工作区下创建 frontend/ 和 api/ 子目录

## 何时创建文件 vs 内联回答

需要创建文件的情况：
- 用户明确要求"生成文件"、"保存"、"下载"
- 代码超过 10 行
- 用户需要独立打开/运行的文件（HTML、完整的脚本等）
- 用户说"写一篇博客/文章/报告"

内联回答即可的情况：
- 策略分析、方案探讨、头脑风暴
- 简短代码示例（几行以内）
- 纯问答（"这个 API 怎么用"）

## 迭代修改规则（用户反馈后）

用户说"不对"、"不行"、"改一下"、"还是有问题"时：

1. 不要假设用户错了——先假设代码有问题
2. 不要重写整个文件——那会引入新 bug 且丢掉已有正确逻辑
3. 用 search_content 找到相关代码，用 read_file 确认，用 replace_in_file 精准修改
4. 如果连续两次修改都没解决问题，重新思考：是不是理解错了用户的需求？
5. 涉及视觉效果（颜色、位置、动画、透明度）的问题，优先搜索渲染相关的关键字
6. 如果用户描述了一个视觉问题而你无法看到渲染结果，基于 Canvas/HTML/CSS 的机制做逻辑推理

## 禁止行为

- 严禁跳过搜索直接修改代码
- 严禁仅凭文件名猜测代码逻辑
- 严禁在用户反馈视觉效果不对时，重写整个文件
- 严禁在 final_message 中声称修改了代码但实际没有调用工具
